# Decision Log

Running record of decisions approved by the project owner, recommendations made and
their outcomes, and obligations still outstanding. Updated at the end of every
milestone.

The specification PDF is the contract; this file records the choices the spec left
open, and who decided them. Where a decision contradicts an earlier one, the later
entry wins and the earlier is marked superseded.

**Status legend:** ✅ approved and done · 🔵 approved, not yet built · ⏳ awaiting
decision · ⚠️ outstanding obligation · ❌ rejected or superseded

---

## Process rules (standing)

| # | Rule | Origin |
|---|---|---|
| P1 | Development is gated milestone by milestone (M0–M7). Work on a milestone begins only after the previous one is **explicitly approved**. | Owner, at project start |
| P2 | A failed exit criterion stops work. Diagnose and report; do not request approval for the next milestone. | Owner, at project start |
| P3 | A milestone is never marked complete on incomplete, skipped, mocked-away, or assumed results. | Owner, at project start |
| P4 | Each milestone lands on its own branch, opens a PR, and is **merged before the next milestone starts**. | Owner, at M2→M3 |
| P5 | CI must actually run and pass — local equivalence is not accepted as evidence. | Owner, at M0 |
| P6 | No live billable provider calls, no raw prompt/output storage, no weakening of privacy or budget guarantees, no public-API semantic changes without explicit approval. | Owner, at project start |

## M1 — Persistence ✅ approved, merged (PR #3, `4270505`)

**Exit gate:** *Migration and round-trip tests both DBs.* — verified on SQLite and PostgreSQL 16.

### Decisions approved

| # | Decision | Rationale |
|---|---|---|
| D1.1 | **Docker available**; PostgreSQL runs as a real container locally and as a CI service | Owner confirmed. Makes the both-DBs gate genuinely testable. |
| D1.2 | **Money stored as scaled-integer nanodollars on SQLite**, `NUMERIC(20,9)` on PostgreSQL | Correctness, not optimisation: SQLAlchemy's `Numeric` round-trips through `float` on SQLite, violating the never-binary-float invariant. |
| D1.3 | **Node action bump folded into M1** | Owner's direction rather than churning the M0 PR. |
| D1.4 | Branch named `m1-persistence` | Owner's choice; set the `mN-topic` convention. |
| D1.5 | **Legal state-transition table deferred to M5**, where the state machine lives | The Codex checklist sequences it at step 2, but it is not in M1's gate. |
| D1.6 | **`GATEWAY_HASH_KEY` fails startup in staging/prod** while left at the development default | Digests are what stand between telemetry and prompt text; a public key makes short prompts brute-forceable. |
| D1.7 | **Migrations never run at boot** — pending migrations are a readiness failure | An operator applies them; a starting replica must not mutate a schema its peers serve. |

### Recommendations and outcomes

| Recommendation | Outcome |
|---|---|
| Keep the virtualenv **outside iCloud** (`~/.virtualenvs/…`) — iCloud re-applies macOS `UF_HIDDEN` to `__editable__*.pth`, and CPython ≥3.12 skips hidden `.pth`, so `pip install -e` silently no-ops **repeatedly** | ⚠️ **Still open** — see R1 |
| CI must fail if the PostgreSQL matrix silently skips | ✅ Implemented — guard job |

### Defects found by tests

Three portability defects, each invisible on one backend:

1. **`WINDOW` is reserved in PostgreSQL.** SQLite accepted `budgets.window`; Postgres
   rejected the check constraint, whose raw SQL is not auto-quoted. Renamed `window_kind`.
2. **Autogenerated JSONB emitted dialect imports the migration lacked** — `NameError` on
   first run. JSON is now a portable `JSONDocument` type.
3. **Migrations were never stamped.** SQLAlchemy 2.0 has no autocommit and SQLite reports
   non-transactional DDL, so `CREATE TABLE`s persisted while the `alembic_version` INSERT
   rolled back — a schema reporting itself at *no revision*.

## M3 — Routing ✅ approved, merged (PR #5, `ab103fe`)

**Exit gate:** *Eligibility/determinism suite.* — 31 + 26 tests.

### Decisions approved

| # | Decision | Rationale |
|---|---|---|
| D3.1 | **Routing priors live in registry data** (`latency_prior_ms`, `pass_rate_prior`, `failure_rate_prior`, `priors_source`), not hardcoded in the scorer | Proposed and approved so measured values later replace *data*, not code. §10 requires priors to carry a source. |
| D3.2 | **Deterministic heuristic classifier**, not a model | A non-deterministic classifier would make identical requests route differently and break the inspect/execute parity §4 requires. Never raises; falls back per §7. |
| D3.3 | **Score components normalised across the candidate set**, not against fixed constants | See defect below. |
| D3.4 | **Ceilings take the minimum across all layers** (`max_cost`, `max_latency_ms`) | The only reading consistent with "never exceed the caller's cost ceiling": neither side may raise a limit the other set. |
| D3.5 | **Every gate evaluated, not short-circuited** | Inspection must explain *all* exclusion reasons. |
| D3.6 | **Inspect 404s on unknown explicit models**, matching generation | Inspect must not bless a route execute would reject. |
| D3.7 | **14 task-class policy fixtures** seeded (§14 requires ≥10) | |

### Defects found by tests

1. **Scoring normalisation was inert.** Against fixed constants, a realistic cost (~$0.001)
   normalised to ~0.005 while latency spanned ~0.9 — the cost weight barely mattered and
   `auto-cheap` selected the *expensive* model. For a token-balancing gateway, close to the
   worst available defect.
2. **Control-precedence bug carried from M2.** Deployment *defaults* sat in the
   highest-precedence layer, so **a caller could never set a tighter ceiling than the
   default**. Fixed by D3.4.

### Process note

The M3 commit initially landed as a **root commit** on a stale local branch (the first PR
attempt failed with "no commits between"). Rebuilt properly parented on `main`; the
resulting tree was verified byte-identical with all tests passing.

## M4 — Budgets and Providers ✅ approved, merged (PR #6, `3b8ee1a`)

**Exit gate:** *Concurrency/failure suite.* — verified in CI
([run 31418776327](https://github.com/alrdarm/LLM_token_balancing_gateway/actions/runs/31418776327),
481 tests, both backends).

### Decisions approved

| # | Decision | Rationale |
|---|---|---|
| D4.1 | **Concurrency tests use real threads against real databases**, not mocked sessions | Owner's choice. The invariant lives in transaction isolation and lock ordering; a mock proves none of it. Accepts slower, occasionally timing-sensitive tests. |
| D4.2 | **Adapter plan: Option A + alien fake** — deterministic fake, alien-shaped fake, OpenAI-compatible HTTP, CommandCode CLI | Owner's choice. M4's stated scope is *"fake + one HTTP + CLI"*; the OpenAI-compatible adapter is near-identity, so an intentionally alien fake keeps the abstraction honest at the cost of a fixture rather than an integration. |
| D4.3 | **Adapters translate, never decide** — no internal retries | A retry inside an adapter spends money the budget manager never reserved. |
| D4.4 | **Settlement takes the same locks as reservation**, in the same order | See defect below. |
| D4.5 | **Gemini and Anthropic adapters deferred** to a later milestone | §14 requires all four before release — see R4. |

### Defects found by tests

**Settlement was losing money under concurrency, and only PostgreSQL revealed it.**
`settle`/`release` are read-modify-writes on `reserved`/`spent` that read without locking;
under READ COMMITTED two concurrent settlements read the same balance and both write back,
dropping one update. SQLite's whole-database write lock hid it completely. It surfaced as
exactly one failing test on the Postgres half — the case for the both-backends matrix in a
single data point.

## M5 — Orchestration ✅ approved, merged (PR #7, `49a8d00`)

**Exit gate:** *Non-stream E2E suite.* — 53 E2E tests covering §12 scenarios.

### Decisions approved

| # | Decision | Rationale |
|---|---|---|
| D5.1 | **The orchestrator reuses the frozen `RoutePlan`** rather than re-planning per escalation step | Recommended and accepted. Escalation walks the frozen candidate list, which is what makes §12 T08 inspect/execute parity hold; re-planning would let a registry change move the route out from under a caller who had just inspected it. |
| D5.2 | **The orchestrator never raises for a terminal state** — it returns an outcome, and the API maps state onto its §9 error | Keeps the state machine free of transport concerns and funnels every exit through one place, so "each terminal path persists a reason" is enforced rather than trusted. |
| D5.3 | **Validator availability is read from the real registry**, not a hardcoded list | See defect below. |
| D5.4 | **Idempotent replay returns 409 naming the original request**, rather than reconstructing a body | §6 stores a response *reference*, not a body, and v0.1 retains no responses. The provider is not called again, which is what T06 protects. Fabricating a reply would be dishonest. |
| D5.5 | **`independent_review` and `rubric_judge` ship as an explicit stand-in** | A real judge is a billable provider call recorded as its own attempt (§6 `validator_attempt_id`). The build order says finish orchestration against fake validators first. The stand-in never claims to have assessed quality. |
| D5.6 | **`dry_run` reuses the inspection serializer** | A dry run and `/route/inspect` cannot then describe the same request differently. Closes R3. |

### Defects found by tests

1. **Planning checked validator availability against a fiction.** A hardcoded list, not the
   registry, so §10 step 5 admitted routes whose validators did not exist — and the shortfall
   surfaced only *after* the provider had been paid.
2. **Idempotency record was written before its request row**, violating the foreign key. Fixed
   by persisting the request first, inside the same uncommitted transaction so a conflict
   leaves nothing behind.

### Test premises that were wrong (not bugs)

Recorded because both look like failures and are not:

- A **released** attempt costs nothing, so it correctly does not count against the request
  ceiling. The mid-request ceiling test had to be rebuilt around attempts that actually settle.
- A ceiling low enough to matter **narrows eligibility at planning time**, so whether the
  ceiling or the attempt cap stops a run first depends on the candidate set. §8 treats both as
  legitimate stops, so the test asserts the invariant (spend never crosses the ceiling) rather
  than pinning one stop rule.

## M7 — Hardening ⏳ provisional — PR open, awaiting approval

**Exit gate:** *Acceptance checklist.* — `docs/ACCEPTANCE.md`, scored honestly.

### Decisions approved

| # | Decision | Rationale |
|---|---|---|
| D7.1 | **M7 scoped as option (a)**: finish hardening, produce an acceptance report honest about unmet criteria, rather than expanding scope or descoping §14 | Recommended and accepted. Keeps hardening clean and puts the R4/R11 decision in front of the owner with evidence. |
| D7.2 | **Authentication is a pure read** | See defect below. |
| D7.3 | **Redaction combines key matching and pattern matching** | Each misses what the other catches: a field named `api_key` is redacted whatever it holds; a value shaped like a credential is redacted whatever it is called. |
| D7.4 | **Header redaction applies only the secret rule**, not the content rule | Redacting `Content-Type` because it contains "content" would strip the most useful field from every request log while protecting nothing. |
| D7.5 | **The reconciler settles ambiguous reservations rather than releasing them** | Whether the provider was called is unknowable and §11 forbids finding out by retrying. Under-counting spend lets the next request overspend a depleted budget; over-counting merely denies one. |
| D7.6 | **Performance tests are budgets, not benchmarks** | Thresholds an order of magnitude above observed timings, so they fail on a regression *of kind* rather than on a slow runner. A tight threshold produces flaky failures that get muted, and a muted test protects nothing. |

### Defect found by the performance budget

**`authenticate()` wrote `last_used_at` on every authenticated request**, turning
every call — including read-only `/route/inspect` — into a write against a single shared row.
On SQLite this serialised all traffic behind one write lock: 20 concurrent inspections took
**91 seconds with 17 of 20 returning 500** (`database is locked`). On PostgreSQL it would have
been a permanent hot row rather than an outage — worse, in that nobody would have noticed.

Authentication is now a pure read. The same workload completes in **0.02 seconds, 6 of 6
succeeding**. This is the clearest case in the project of a test catching something no amount
of review would have: the code looked entirely reasonable.
